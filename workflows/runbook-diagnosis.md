# runbook-diagnosis：异常诊断

对应命令 `/rtd-diagnose`。**诊断结束不自动变更、不自愈**——要改就走对应 runbook 的门。

## 0 · 输入解析

- 用户给平台链接 → 按 `knowledge/link-parsing.md` 提取身份（链接里的数字段是**作业唯一 ID**，不是引擎 jobId）；链接形式不在已核实清单里 → 保留映射缺口，不猜站点；
- 没链接 → 追问；追问不到 → 按症状分支做平台侧初查。

```
py -3 .rtd/engine/rtd.py object set --source "diagnosis" --file-id "<ID>" --instance-id "<实例>"
```

## 1 · 预检与映射（不可跳过）

1. 按场景发现必要执行器；存储类症状 → 先从运行 DDL / 拓扑确认连接器，只准备**真实用到的**工具，不装全家桶；
2. 身份与时间就绪：ID / 实例 / 版本 / 时区 / attempt 映射；
3. 工具 schema 按需加载（schema 目录是**快照**，不是可用性证明）。

## 2 · 最小诊断循环

1. 明确症状、影响对象、异常窗口、可比基线；已有有效上下文不重复采集；
2. **平台侧**：拓扑/详情定位异常任务 → 指标先看目录再看趋势，有理由才下钻原始采样 → 变更记录核窗口内变更 → 血缘看一层影响（时间相关 ≠ 因果）；
3. **引擎侧**：先做作业身份查询（集群/UI 地址/版本/失败 traceId），再按症状选**最少**调用；每次调用回答一个问题，并写下它支持或反驳了哪条假设；
4. 收窄到异常算子 / 子任务 / 实例；日志必须带窗口 + 关键词 + 行数上限；实例优先指定目标，不扫全部；线程栈 / 剖析只在已有 CPU 或阻塞证据时读；
5. 证据指向存储 → 走存储分支，取源端 / 维表 / 汇端证据，**同窗口、同基线**；
6. 核查反证与其他解释后出结论。

## 3 · 症状分支要点

| 症状 | 先看什么 | 别下什么结论 |
| --- | --- | --- |
| 提交 / 启动失败 | 提交侧 traceId 查提交异常（不必等运行作业产生） | 别用作业唯一 ID 替代提交 traceId |
| 频繁重启 | 运行时异常 + 重启趋势 + 时间线 | 只覆盖当前运行作业；历史作业分开看 |
| 运行中无异常事件 | 按窗口关键词查引擎日志 | 空查询不是健康证明 |
| 延迟 / 反压 | 吞吐趋势 → 总览 → 算子 → 子任务；先核单位与聚合口径 | 热数据、负载、下游、GC 都是**待检假设** |
| 快照失败 / 变慢 | 历史统计定位异常 → 单点详情看慢阶段 | 持续失败/上传内存不足/伴反压要转专项 |
| 运行中但没数据 | 对比源汇速率、源端输入、过滤条件 | RUNNING 只代表调度状态 |
| 资源 / CPU / GC | 集群总览 + 项目余量 → 异常算子 → 实例详情 | 没有阻塞证据就不读线程栈 |

## 4 · 存储侧口径（独立分支）

- 同窗口关联实时侧证据，不要求用户另开一轮；
- 认证在本机完成，**凭据不落聊天、不落报告**；
- 配额有余量只能反驳"该窗口配额耗尽"这一条假设；总量 ≠ 本作业吞吐。

## 5 · 交付

四要素 + 四级分级（已确认 / 较可能 / 已排除 / 未决），每级附支持与反证；**核心结论直接写在回复里**，不只给文件。

修复在包内能力范围内时，附：目标 / 关键入参 / 调用顺序 / 进度追踪方式 / 生效验证步骤——然后交用户决定要不要执行。
