# 版本生效矩阵

全包唯一的"意图 → 版本 → 生效方式"规则源。`runbook-lifecycle.md` 与 `runbook-tuning.md` 都引用本文件，不各写一份。

## 一、先分清三种"版本"

| 概念 | 指什么 | 谁在用 |
| --- | --- | --- |
| 开发态版本 | 编辑、编译、提交、发布动作的载体 | 研发与迁移流程 |
| 运行态版本 | 当前真正在跑的实例所对应的版本 | 运维、巡检、诊断 |
| 待发布版本 | 已提交但还没成为运行态的那一份 | 发布流程；**顶层字段通常表示运行态，待发布内容在专门嵌套字段里** |

拿错层就会得出"我明明改了"的错误结论。

## 二、意图 → 生效方式

| 意图 | 生效方式 | 必须知道的限制 |
| --- | --- | --- |
| 改 SQL / 改任务结构 | 提交 + 发布 + 重启 | 发布成功 ≠ 目标生效，要回读运行态 |
| 只改单个算子的并发 | 保存执行计划 + 部署 | 保存 ≠ 生效；同链发散并发**必须完整重启**，热更新不适用 |
| 改运行参数 | 按意图显式指定作用域 | 默认作用域可能同时影响两层版本；写后要重新查询核实，不能拿返回的前后值当两份独立快照 |
| 热更新 | 仅限特定组合 | 不保证运行参数即时生效，**不得承诺**；不能带恢复点参数 |
| 停止 / 下线 | 平台侧动作 | 取消部署 ≠ 停止；进度查询可能推进清理 |
| 回刷历史数据 | 显式范围回刷 | 范围必须用户确认；禁止用"补数"掩盖口径问题 |

## 三、阈值与节奏

轮询间隔、超时上限、巡检预算等**全部数字**只写在项目级 `.rtd/config.json` 的 `limits` 段；工作流只写"按配置 `limits` 执行"。默认值示例见 `templates/config.example.json`。

## 四、验证清单（每次改完都要过）

1. 状态回读：目标是运行态就核运行态，是配置就核配置回读；
2. 版本比对：实际生效版本 = 本次提交的版本；
3. 物理结构：涉及并发/算子调整时回读物理结构，不只看逻辑配置；
4. 失败态：出现"已部署待验证"就如实写这个状态，不写成"完成"。
